0.2How the pieces stack

Read the picture as a call stack. Your script calls LLM.generate. The engine decides, on the CPU, which sequences run in the next step and where their keys and values live in GPU memory. The runner turns that decision into tensors, runs the model, and returns one sampled token per sequence. The model is an ordinary PyTorch module tree whose leaves are the layer files.

0.3Five ideas the code assumes

Each idea below names where it lives in this repository, so you can jump ahead if you already know it.

Prefill and decode
A request starts with a prefill: the whole prompt goes through the model in one forward pass, which writes every prompt token's keys and values (K/V) into a cache and produces the first output token. After that, each decode step feeds exactly one new token per sequence. Prefill is compute-bound and has many tokens per sequence; decode is memory-bound and has one. nano-vllm never mixes the two inside one step (Step 06).
KV cache
Attention for token t needs the K/V of every earlier token, at every layer. Keeping them on the GPU means a decode step only computes K/V for the one new token. For Qwen3-0.6B that cache costs 112 KiB per token (Step 07.4).
Paged KV
The cache is cut into fixed-size blocks of 256 token slots. A sequence owns a list of block ids, its block table, which do not have to be adjacent. That removes fragmentation and lets two sequences point at the same block when they share a prompt prefix (Step 05).
Continuous batching
The batch is rebuilt every step. Finished sequences leave and waiting ones join between steps, so the GPU stays busy without waiting for the slowest request in a fixed batch (Step 06).
Tensor parallelism
With tensor_parallel_size = N, N processes each hold 1/N of most weight matrices and 1/N of the attention heads, and combine partial results with NCCL collectives (Step 10.1).

1.2example.py: the smallest real use

1.3bench.py: the throughput benchmark

  • 256 requests with prompts of 100–1024 random token ids drawn from [0, 10000], and max_tokens drawn from 100–1024. seed(0) makes the workload repeatable.
  • ignore_eos=True makes every request produce exactly max_tokens tokens, so the total output token count is known in advance.
  • enforce_eager=False turns CUDA graphs on; max_model_len=4096 covers the longest request (1024 + 1024).
  • A one-prompt generate(["Benchmark: "], SamplingParams()) runs before the timer starts, so first-call costs stay out of the measurement.
  • Throughput is output tokens divided by wall time, and the wall time includes all prefill work.
  • The commented lines switch the same script to vLLM, which takes token-id prompts as dict(prompt_token_ids=p).

2.2SamplingParams: per-request decoding

Three fields. The assertion forbids temperature 0: the sampler divides logits by the temperature (Step 10.7), so greedy decoding is not available. There is no top-k, top-p or repetition penalty. Step 03The engine loop: LLMEngine

LLMEngine owns the tokenizer, the scheduler and rank 0's model runner, and spawns the other ranks. Its generate method is a loop around step(), and each step is one schedule, one forward, one round of bookkeeping.

3.1Construction, and why the order matters

  1. Filter kwargs into Config. dataclasses.fields(Config) gives the allowed names; everything else is dropped.
  2. Set Sequence.block_size. It is a class attribute, so every Sequence in this process uses the configured block size for num_blocks and friends. The assignment happens only in the main process (see Step 14 for what that means for workers).
  3. Spawn ranks 1…N−1. mp.get_context("spawn") starts fresh interpreters, which CUDA requires; a forked child cannot reuse the parent's CUDA context. The process target is the ModelRunner class itself, so constructing it is the whole life of the worker: its __init__ ends in self.loop(). Each worker gets one Event; rank 0 later receives the list of all of them.
  4. Build rank 0's ModelRunner in this process. It must come after the spawns because init_process_group blocks until all ranks have joined. This call loads the model, measures memory, allocates the KV cache and captures CUDA graphs (Step 07).
  5. Load the tokenizer and record EOS. config.eos is set after the workers were spawned, so their copies of config keep −1. They never need it.
  6. Build the Scheduler last. Its BlockManager needs config.num_kvcache_blocks, which only exists after step 4. Spawned workers received a pickled copy of config earlier, so this value is rank 0's own measurement.
  7. Register exit with atexit, so workers are told to stop when the interpreter exits.

Step 05Paged KV memory: BlockManager

BlockManager is a CPU-side allocator for GPU memory it never touches. It hands out block ids, counts how many sequences share each block, and remembers which token prefixes each block holds so later requests can reuse them.

5.1Blocks, block tables and slots

The physical pool is one big tensor allocated by the runner (Step 07.4). The block manager only deals in integer ids from 0 to num_kvcache_blocks − 1. Two numbers follow from a block table and a position: the block block_table[pos // block_size] and the slot block_id × block_size + pos % block_size. The runner computes slots; the block manager decides which ids appear in the table.

5.2Block and the four bookkeeping structures

A Block records how many sequences use it (ref_count) and, once it is full and computed, the hash of the prefix it completes and its token ids. reset() sets ref_count to 1, not 0, because it is only called on a block that is being handed to a sequence.

5.4can_allocate: count cache hits, check capacity

The scheduler calls this before admitting a waiting sequence that has no blocks yet. It changes nothing; it answers how many leading blocks are cache hits, or −1 if the sequence cannot fit.

  1. Walk the logical blocks, recomputing the hash chain. Stop at the first block whose hash is unknown or whose stored token ids differ. The token comparison protects against a 64-bit hash collision.
  2. The loop runs to num_blocks − 1, so the last block is never matched, even when the prompt is block-aligned and fully cached. At least one block's worth of tokens is always computed, and its final position produces the logits for the next token.
  3. num_new_blocks starts at the full block count. A hit on a block that is in use by another sequence costs no new memory, so it is subtracted. A hit on a block sitting in the free deque still has to be taken out of the deque, so it still counts.
  4. Return −1 if the free deque is shorter than num_new_blocks, otherwise the number of cached blocks.

5.5allocate: build the block table

  • For each cached block, recompute the hash and look it up. If the block is in use, increment its ref_count. If it is free, bring it back: ref_count = 1, remove it from the free deque (an O(n) deque.remove), add it to the used set. Its contents are untouched, so no recomputation is needed.
  • Every remaining logical block gets a fresh block from _allocate_block. The whole sequence is allocated at once, even if chunked prefill will fill it over several steps.
  • num_cached_tokens becomes num_cached_blocks × block_size; prefill will start computing at that position.

6.2Prefill phase and chunked prefill

Prefill always goes first. If anything at all is scheduled in this loop, the step is a prefill step and no sequence decodes in it.

  1. First come, first served. The loop only looks at waiting[0]. When the head cannot be served it breaks; it never skips ahead to a smaller request.
  2. Budget. remaining is what is left of max_num_batched_tokens. A batch that has used it all stops.
  3. Fresh or continuing. A sequence without blocks is new or was preempted: can_allocate reports cache hits or −1, and the work is everything after the cached blocks. A sequence that already has blocks is mid-way through a chunked prefill, and its work is everything after num_cached_tokens.
  4. The chunking rule. If the work does not fit in remaining and the batch already has a sequence, stop. Only the first sequence of a batch can be cut. That sequence always sees the full budget, so in practice a prompt is chunked only when its uncached part is longer than max_num_batched_tokens. With the defaults (16,384 tokens of budget, max_model_len 4,096) that never happens; lower the budget or raise max_model_len to see it.
  5. Commit. Blocks are allocated only now that the sequence is definitely in the batch. num_scheduled_tokens is the work, capped by the budget.
  6. Done or not. If this chunk reaches num_tokens, the sequence becomes RUNNING and moves to running. Otherwise it stays at waiting[0]; it used the whole remaining budget, so the next iteration hits remaining == 0 and the loop ends.

6.3Decode phase and preemption

  1. Only reached when nothing could be prefilled.
  2. Take sequences from the front of running, up to max_num_seqs.
  3. Make sure the sequence can store one more token (can_append). While it cannot, preempt the sequence at the back of running, the most recently admitted one, which frees its blocks. If no other sequence is left, preempt this one and move on.
  4. Python's while … else: the else block runs when the loop condition turns false, meaning there is room, and is skipped after the break that follows self-preemption. In the else branch the sequence is set to compute one token, marked is_prefill = False so it pickles compactly, and given a new block if it needs one.
  5. assert scheduled_seqs fires only if a single sequence needs more blocks than the whole pool, because then even preempting everything else frees nothing usable.

6.4preempt: give memory back, recompute later

The victim goes back to WAITING, is marked as prefill again, loses all its blocks and is put at the front of waiting, so it is the first sequence re-admitted. There is no swapping to CPU memory; the K/V will be recomputed. Two details make that cheaper than it sounds:

  • deallocate keeps hashes, and decode steps hashed every block they filled. When the sequence is re-admitted, can_allocate finds all of its full blocks that have not been recycled yet, and only the rest is recomputed.
  • The last token of a preempted sequence was sampled but never fed back. The re-prefill computes it, so the token sampled at the end of that prefill is a correct next token and postprocess appends it.

6.5postprocess: apply the sampled tokens

  1. hash_blocks first, while num_cached_tokens and num_scheduled_tokens still describe what was just computed.
  2. Advance num_cached_tokens, clear num_scheduled_tokens.
  3. A prefill chunk that did not reach the end of the sequence produced a token for a position in the middle of the prompt. It is discarded with continue.
  4. Otherwise append the token. Finish when the token is EOS (unless ignore_eos) or the completion has reached max_tokens. The token is appended before the check, so a finishing EOS is part of the output.
  5. A finished sequence frees its blocks immediately and leaves running (an O(n) deque.remove).

    Step 07From sequences to tensors: ModelRunner

    One ModelRunner exists per GPU. It builds the model, measures memory, owns the KV cache, captures CUDA graphs, converts a list of Sequences into the flat tensors FlashAttention wants, and, on rank 0, samples. On other ranks it is a loop that waits for instructions.

    7.4allocate_kv_cache: size the pool from what is left

    Four memory numbers are read right after warmup:

    total, free
    torch.cuda.mem_get_info(), device-wide. used = total − free includes the CUDA context, other processes on the GPU and everything PyTorch holds.
    current
    Bytes PyTorch has allocated right now: essentially the weights.
    peak
    The highest allocation during warmup: weights plus the worst activations.

    The KV budget is total × gpu_memory_utilization − used − (peak − current): the allowed share, minus what is in use, minus room to bring the activation peak back. Dividing by the size of one block gives num_kvcache_blocks, written into config for the scheduler to read.

    One block stores K and V (the factor 2) for every layer, block_size tokens, and this rank's KV heads:

    block_bytes = 2 × num_hidden_layers × block_size × (num_key_value_heads / tp) × head_dim × dtype.itemsize

    For Qwen3-0.6B at tp = 1: 2 × 28 × 256 × 8 × 128 × 2 = 29,360,128 bytes, exactly 28 MiB per block, or 112 KiB per token.

    7.5prepare_prefill: pack a varlen batch

    For each sequence, the new tokens are [num_cached_tokens, num_cached_tokens + num_scheduled_tokens). The function builds:

    input_ids, positions
    The new tokens of all sequences, concatenated, and their absolute positions. Positions start at start, so a second chunk or a prefix-cache hit continues the numbering RoPE needs.
    cu_seqlens_q
    Running sum of new-token counts: where each sequence's queries begin in the packed batch.
    cu_seqlens_k
    Running sum of seqlen_k = end: each sequence attends to its cached prefix plus its new tokens.
    max_seqlen_q, max_seqlen_k
    Longest of each; FlashAttention needs them to size its work.
    slot_mapping
    One slot per new token. The loop visits the blocks the range touches; the first block starts at start % block_size, the last ends at end − i × block_size, and blocks in between contribute all their slots.
    block_tables
    Only when cu_seqlens_k[-1] > cu_seqlens_q[-1], meaning at least one sequence has cached context. Then attention must read K/V for those earlier positions from the cache, so every sequence's table is passed. Otherwise None, and attention uses the freshly computed k and v.

    Each list becomes a pinned CPU tensor copied to the GPU with non_blocking=True, so the copies overlap with Python work. set_context receives everything positionally; context_lens is None in prefill.

    7.9capture_cudagraph: one graph per batch bucket

    A CUDA graph records a fixed sequence of kernel launches with fixed tensor addresses and replays it with a single launch, removing per-kernel CPU overhead. Decode is where that overhead dominates: a decode forward is hundreds of small kernels for a few tokens.

    • Static buffers sized for the largest batch: input_ids, positions, slot_mapping, context_lens, block_tables (width ceil(max_model_len / block_size), 16 by default) and outputs ([max_bs, hidden_size]).
    • Buckets: 1, 2, 4, 8, then every multiple of 16 up to max_bs = min(max_num_seqs, 512). That is 36 graphs with the defaults.
    • Largest first. All graphs share one memory pool, taken from the first (largest) capture, so smaller graphs reuse its memory instead of each reserving their own.
    • For each size: point the context at slices of the static buffers, run once eagerly as a warmup, then capture the same call. Because Attention and the LM head read the context at Python level during capture, the recorded kernels are bound to those buffer addresses, and replay picks up whatever the buffers hold at that moment.

    Step 08The side channel: Context

    10.4layernorm.py: RMSNorm with a fused residual add

    RMSNorm scales each vector by the inverse root-mean-square of its elements, then by a learned weight: y = x / sqrt(mean(x²) + eps) × w. There is no mean subtraction and no bias.

    • The statistics are computed in float32 and the result is cast back before multiplying by the weight, matching Hugging Face's Qwen3 implementation.
    • The in-place mul_ calls work on the float32 copy, never on the caller's tensor.
    • add_rms_forward adds the residual in float32, keeps the sum, cast to model dtype, as the new residual, and normalises it. Under @torch.compile the add, the reduction and the scaling fuse into one or two generated kernels instead of a chain of separate ones.
    • The same class normalises per head for QK-norm: it reduces over the last dimension, whatever the leading shape.

    10.5rotary_embedding.py: RoPE

    Rotary embeddings rotate pairs of query and key components by an angle proportional to the token's position, so the dot product between a query and a key depends on their distance. Frequencies are θ_j = base^(−2j / d) for j = 0 … d/2 − 1.

    • The constructor precomputes cos and sin for every position up to max_position_embeddings and stores them concatenated in a [max_pos, 1, head_dim] buffer (cos in the first half, sin in the second). The size-1 axis broadcasts over heads. persistent=False keeps it out of the state dict.
    • forward gathers rows by positions and rotates q and k. Positions come from the runner, so chunked prefill and prefix hits get the right angles with no extra work.
    • apply_rotary_emb pairs element j with element j + d/2 (the rotate-half layout used by GPT-NeoX and Hugging Face Qwen), not adjacent elements. It computes in float32.
    • rotary_dim must equal head_size; partial rotary is not supported.
    • @lru_cache(1) on get_rope returns the same module for identical arguments, so the table is built once per model.

    10.7sampler.py: temperature and the exponential race

    Logits are divided by each row's temperature and turned into probabilities with softmax. The token is then argmax(p_i / E_i), where each E_i is an independent Exp(1) draw. This picks token i with probability exactly p_i: E_i / p_i is exponential with rate p_i, and the smallest of several independent exponentials is the one with rate p_i with probability p_i / Σp = p_i. It is the Gumbel-max trick written without logarithms.

    Everything is elementwise plus one argmax, so the whole sampler compiles into a couple of kernels and avoids torch.multinomial. clamp_min_(1e-10) guards against dividing by a zero draw.

    nanovllm/layers/sampler.pyL1–12GitHub ↗

    Step 14Sharp edges and limits

    Behaviour found while reading the code for this guide. The first three are bugs that a particular configuration triggers; the rest are limits worth knowing before you build on the engine.

    14.1Request length is not checked

    Nothing compares len(prompt) + max_tokens with max_model_len.     14.4Each rank sizes its own KV pool

    Every rank runs allocate_kv_cache against its own GPU's free memory, but the scheduler allocates block ids using rank 0's count. If another rank had less free memory (another process on that GPU, for example) it has fewer blocks than rank 0 hands out. On identical, otherwise idle GPUs the counts match.

    14.5One tensor-parallel engine per machine

    The NCCL rendezvous port (2333) and the shared-memory name ("nanovllm") are hard-coded. A second engine with tp > 1 on the same machine collides with the first. A run that dies without reaching exit can leave the "nanovllm" segment behind, and the next SharedMemory(create=True) then fails with FileExistsError. The segment is 1 MiB; a pickled step must fit in it.

    14.6Scheduling policy

    • Prefill always wins. While a waiting request can be admitted, no sequence decodes, and a long chunked prompt pauses decoding for every step it takes.
    • Strict first-come-first-served admission: a head request that does not fit blocks smaller ones behind it.
    • running can exceed max_num_seqs; only its first max_num_seqs sequences decode until some finish.
    • Preemption always recomputes; there is no swap to CPU memory.

    14.7API and model coverage

    • Unknown keyword arguments to LLM(...) are dropped silently (2.1).
    • No greedy decoding (temperature must be > 1e-10), no top-k, top-p or penalties, no stop strings, no streaming. Output text includes the EOS token. generate returns dicts despite its list[str] annotation.
    • One architecture: Qwen3, plus Qwen2-style configs with QKV bias. RoPE scaling is not implemented. Head counts and the vocabulary must divide by tp, and (num_key_value_heads / tp) × head_dim must be a power of two for the Triton store kernel.
    • Offline only: one process, one Python call at a time, all ranks on one machine.
    • The code reads hf_config.dtype, which needs a transformers release that exposes dtype on configs.

    block

    A sequence's list of physical block ids, in logical order.

    chunked prefill

    preemption
